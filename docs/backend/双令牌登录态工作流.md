# 基于双令牌方案的用户登录态工作流

## 目标

双令牌方案把“高性能校验”和“可控登录态”拆开处理：

- `short_token` 负责高频请求的本地快速校验，尽量少查 Redis。
- `long_token` 负责兜底续期和最终登录态确认，绑定服务端 Session。
- Redis 中的 Session 负责服务端可控下线、续期和登录态最终裁决。

这套方案结合了纯 Token 方案的性能优势，以及 Session 方案的可控性。

## 两类令牌职责

### 1. long_token

- 含义：长期登录凭证
- 建议有效期：30 天
- 典型格式：`session_id.signature`
- 作用：
  - 标识一个服务端 Session
  - 在短令牌过期时兜底恢复登录态
  - 支持强制下线

### 2. short_token

- 含义：短期访问凭证
- 建议有效期：1 天
- 典型格式：`user_id.device_id.expire_time.signature`
- 作用：
  - 每次请求优先校验
  - 尽量在本地完成验签和过期判断
  - 减少 Redis 和登录服务压力

## 标准登录态工作流

### 1. 用户发起登录请求

用户无论通过 Web、App 还是小程序登录，都会向登录服务提交账号凭证。

### 2. 登录服务校验账号密码并创建 Session

登录成功后，登录服务执行两件事：

- 生成一个 `session_id`
- 在 Redis 中写入用户 Session 数据，过期时间设置为 30 天

Session 中通常保存以下信息：

- `user_id`
- `device_id`
- `client_ip`
- `login_time`
- 其他必要登录上下文

这一步意味着：用户登录态的最终依据仍然掌握在服务端。

### 3. 登录服务生成 long_token 和 short_token

登录服务分别对两类令牌签名并返回给客户端：

- `long_token = session_id + signature`
- `short_token = user_id + device_id + expire_time + signature`

其中：

- `long_token` 对应 Redis 中的 Session
- `short_token` 不依赖 Redis 即可完成本地验签和过期判断

## 请求校验流程

### 4. 客户端后续请求同时携带两类令牌

用户登录成功后，后续所有需要身份校验的请求都携带：

- `long_token`
- `short_token`

令牌可以放在 HTTP Header 中，也可以按网关规范放到自定义请求头中。

### 5. 服务端优先校验 short_token

服务端收到请求后，先校验 `short_token`：

- 如果 `short_token` 合法且未过期，则直接判定用户已登录
- 如果 `short_token` 非法、签名错误、格式错误，应直接要求重新登录
- 如果 `short_token` 仅仅是“已过期”，才进入下一步，用 `long_token` 兜底

这一步的核心目标是提升性能，因为绝大多数正常请求都不需要访问 Redis。

### 6. short_token 过期时，改用 long_token 校验

当 `short_token` 过期后，服务端读取 `long_token` 并执行：

- 验证 `long_token` 签名是否正确
- 如果签名错误或内容被篡改，直接要求用户重新登录
- 如果签名正确，则提取出 `session_id`
- 再根据 `session_id` 去 Redis 查询 Session 数据

### 7. 根据 Session 是否存在，决定是否续发 short_token

如果 Redis 中不存在对应 Session：

- 说明登录态已经失效，或者用户已被强制下线
- 服务端要求客户端重新登录

如果 Redis 中存在对应 Session：

- 说明用户登录态依然有效
- 服务端判定本次身份校验成功
- 同时生成一个新的 `short_token`
- 在响应中把新的 `short_token` 返回给客户端

### 8. 客户端静默更新 short_token

客户端收到成功响应后，更新本地保存的 `short_token`，继续后续请求。

这一过程对用户应当是无感的：

- 用户不需要重新登录
- 前端只是在后台静默替换掉过期的短令牌

## 强制下线机制

如果服务端需要强制某个用户下线，最直接的方式就是删除 Redis 中对应的 Session 数据。

这样做之后：

- 用户现有的 `long_token` 仍然可能格式合法
- 但一旦服务端通过 `session_id` 去 Redis 查询不到 Session
- 就会判定登录态失效并要求重新登录

这就是双令牌方案可控性的关键来源。

## 方案权衡

### 优点

- 大多数请求只校验 `short_token`，性能高
- 登录态最终由 Session 决定，可控性强
- 支持强制下线
- 支持短令牌静默续期，用户体验好

### 代价

- 强制下线不是绝对实时的
- 如果 `short_token` 还没过期，客户端在短时间内仍可能继续访问
- `short_token` 越短，强制下线越及时，但续期频率越高，Redis 和认证服务压力也越大

因此，短令牌时长需要在以下因素之间平衡：

- 安全性
- 用户体验
- Redis 压力
- 认证服务吞吐

## 现状说明

从“完整双令牌工作流”的角度看，当前仓库实现与理想流程基本一致，但仍有两个值得注意的点：

### 1. 校验接口目前更偏单 token 入参

`ValidateToken` 当前使用的是单个 `token` 字段。  
如果要严格落实“双令牌同时携带、短令牌过期后再用长令牌兜底”的流程，网关层需要明确区分并传递：

- `short_token`
- `long_token`

### 2. 短令牌续发需要明确回传路径

理想流程中，服务端在 `short_token` 过期但 `long_token` 仍有效时，应把新的 `short_token` 回写给客户端。  
当前仓库里已经有独立的 `RenewToken` 逻辑，但网关和客户端是否已经完全按“自动续发并静默替换”的模式串起来，还需要结合调用链继续核对。

## 结论

对于用户规模较大、既要性能又要登录态可控性的系统，双令牌方案通常比纯 Session 或纯 JWT 更均衡：

- 短令牌承担高频校验
- 长令牌承担续期兜底
- Redis Session 承担最终登录态裁决

这样既能降低高频请求对 Redis 的依赖，又保留了服务端对登录态的控制能力。
